# QA y operación — Primer parcial TGA04, periodo 2026-3

## Política vigente

- Nueve preguntas; 50 minutos desde el inicio confirmado por el servidor.
- Siete envíos evaluables por pregunta. **Sin descuento por reintentar.**
- Errores de Python, fallos de carga y ejecuciones sin salida no consumen envíos.
- Se conservan las reglas anteriores de salidas de pantalla y hasta tres extensiones de cinco minutos. Esta corrección no recalcula notas históricas.
- La reanudación normal se hace en **la misma pestaña**, ingresando el mismo documento. Una recarga no concede otros 50 minutos.

## Qué cambió

- Python se ejecuta en un Web Worker. Un watchdog externo detiene una ejecución bloqueante y permite volver a ejecutar, sin congelar la interfaz.
- Q2 admite un mensaje descriptivo sin imponer una frase literal. Q7 solicita cifras (mayor/menor), no nombres de meses. Q9 relaciona cada etiqueta con su cifra y permite redacciones equivalentes.
- Se aceptan formatos convencionales de salida numérica. Esto no cambia la sintaxis de los números en Python.
- Q8 verifica la salida y evidencia mínima de entradas y operación; no impone nombres de variables nuevos. No es un sistema de verificación de autoría ni una prueba semántica completa del algoritmo.
- Cada envío tiene un identificador idempotente. La aplicación no avanza antes de que el servidor confirme el guardado.
- El resultado final solo aparece tras confirmación del servidor o lectura de un resultado final ya confirmado. Cero se conserva como cero.
- Se guardan checkpoints y se usa un respaldo temporal por documento/periodo en `sessionStorage` para recuperar borradores o envíos pendientes tras una recarga. **El respaldo temporal no equivale a una entrega.** No se usa `localStorage` para respuestas o notas.
- El respaldo temporal no sobrevive necesariamente al cierre de la pestaña o al borrado de datos del navegador. No cambiar de dispositivo durante el intento; avisar al docente ante pérdida de la pestaña original.

## Archivos principales

- `index.html`: preguntas, interfaz y coordinación del intento.
- `js/python-executor.js`, `js/python-worker.js`: ejecutor aislado.
- `js/exam-grading.js`: evaluación de salida.
- `js/exam-persistence.js`: cola de operaciones, token y respaldo temporal.
- `supabase/migrations/002_reliable_sessions.sql`: sesiones, respuestas por sesión y RPC específicas.

## Despliegue y datos

Aplicar `002_reliable_sessions.sql` **antes** de publicar el frontend nuevo. La migración es aditiva: no elimina ni actualiza registros históricos. No ejecutar de nuevo `001_initial.sql` sobre producción.

Las nuevas tablas son `pparcial_sesiones` y `pparcial_respuestas_sesion`. Sus datos no tienen lectura anónima directa. Las RPC nuevas requieren un token aleatorio de sesión; esto no convierte el acceso por documento del sistema original en una autenticación institucional. Las políticas y el panel administrativo anteriores deben auditarse por separado antes de afirmar seguridad integral.

La nota final se calcula sobre respuestas confirmadas de la sesión, conservando las penalizaciones de tiempo extra y salidas. Se agrega un resumen a la tabla histórica de intentos solo cuando ese documento no tiene un resumen anterior. La nueva tabla de sesiones es la fuente por periodo; no se sobreescriben notas previas. **Las respuestas 2026-3 se escriben exclusivamente en `pparcial_respuestas_sesion`**, vinculadas a una sesión con periodo. No se copian a `pparcial_respuestas`, porque esa tabla histórica no permite distinguir periodos. El panel antiguo solo consulta resúmenes de intentos; el detalle nuevo se consulta en las tablas por sesión.

**Diferencia real de esquema:** la tabla histórica `pparcial_intentos` desplegada no tiene una restricción única por documento, aunque la migración inicial del repositorio la declara. La nueva entrega no depende de `ON CONFLICT(documento)` y se ha probado contra el esquema real.

## Pruebas sin datos académicos reales

```sh
CHROMIUM_PATH=/ruta/al/chrome-headless-shell \
node node_modules/@playwright/test/cli.js test \
  tests/access.spec.js tests/python-runner.spec.js tests/exam-flow.spec.js \
  tests/grading-qa.spec.js tests/persistence.spec.js tests/worker-qa.spec.js \
  tests/visual-qa.spec.js tests/expiry-regression.spec.js
```

- Pyodide es real; no se sustituye por respuestas Python inventadas.
- La persistencia en navegador usa un servidor de prueba en memoria y bloquea el host de producción. Los contratos de parámetros RPC se contrastan con la migración.
- La base de datos se verifica además con SQL real dentro de una transacción con `ROLLBACK`: matrícula, token, revisiones, idempotencia, tiempo, extensiones, nota cero, límites de envíos y preservación de históricos.
- `tests/backend-regression.sql` contiene solo fixtures sintéticas y aserciones. Ejecutarlo únicamente dentro de `BEGIN; … ROLLBACK;`, nunca como importación de estudiantes.
- El panel administrativo anterior no forma parte de esta suite de cambios; sus pruebas heredadas y su autenticación requieren una revisión independiente.

## Consultas docentes (SQL Editor, no en el frontend público)

```sql
SELECT documento, nombre, estado, nota_final, deadline_at,
       extensiones_usadas, finalizado_en,
       snapshot -> 'pendingForReview' AS envio_tecnico_para_revision
FROM public.pparcial_sesiones
WHERE periodo = '2026-3'
ORDER BY creado_en;
```

En caso de entrega técnica pendiente, revisar el código adjunto y las respuestas confirmadas antes de decidir una corrección de nota. Nunca tratar un respaldo local o un mensaje de error como una entrega exitosa.

## Integridad (bloqueos y penalizaciones)

Implementado en `js/exam-integrity.js`. Una página web **no puede impedir** capturas de pantalla ni que el estudiante cambie de aplicación; estas medidas lo dificultan, lo detectan y lo penalizan:

| Medida | Efecto |
|---|---|
| Pegar o arrastrar texto en el editor | Bloqueado. **−0.1** por intento |
| Perder el foco (otra app, ventana o monitor), ocultar la pestaña, salir de pantalla completa | **−0.1** por salida. Varios eventos del mismo instante cuentan como una sola salida |
| Copiar, cortar, menú contextual, seleccionar el enunciado | Bloqueado; solo se registra (sin penalización) |
| Pantalla completa | Obligatoria en computador (si se sale, aparece un aviso para volver). En Chrome/Edge se activa Keyboard Lock: Esc debe mantenerse presionado |
| Celular | **Permitido.** Cambiar de aplicación se penaliza igual. En iPhone no existe pantalla completa para páginas web, por eso no se exige |
| Marca de agua | Nombre y documento del estudiante sobre toda la página: una captura compartida identifica a quien la tomó |

Las penalizaciones suman en `penalSalidas` del checkpoint, que es lo que la base de datos usa al calcular la nota (−0.1 c/u). El desglose queda en `snapshot -> 'integridad'` (`foco`, `pestana`, `pantalla`, `pegar`, `copiar`).

El panel administrativo de TGA04 muestra solo el total de penalizaciones (`pparcial_intentos.penal_salidas`). Para ver el desglose por estudiante (consulta de solo lectura en el SQL Editor):

```sql
SELECT documento, nombre, estado, nota_final,
       (snapshot ->> 'penalSalidas')::int AS penalizaciones,
       snapshot -> 'integridad' AS desglose
FROM public.pparcial_sesiones
WHERE periodo = '2026-3'
ORDER BY nombre;
```
